# Demo app

Open the pages directly in a browser; no server or internet is needed.

| Page | What it shows |
|---|---|
| `wejha.html` | Basket Growth: ranked add-on offers for a basket, display-layout comparisons and an editable profit scenario |
| `planner.html` | Preparation plan with the 16:00 top-up, Day explorer, Why tab, evidence on outside factors, and pilot log |

The `*_data.js` files are generated; rerun the script instead of editing them:

| File | Generated by |
|---|---|
| `recommendation_data.js` | `python src/basket_recommender.py train` |
| `wejha_data.js` | `python src/wejha_layout.py` |
| `preparation_data.js` | `python src/growth_plan.py --export-preparation` (uses the selected v2 preparation model) |
| `why_data.js` | `python src/why_drivers.py` |
| `evidence_data.js` | `python src/external_factor_test.py` |
| `day_data.js` | `python src/day_ledger.py` |

`check_ui.js` checks the frontend ranking logic and data contracts: `node app/check_ui.js`.

# Planner tabs and pilot log (moved from README)

## Demo interface and pilot log (Claude Code teammate 2, Marwa)

`app/planner.html` is a single offline page. Open it in a browser; it needs no server or network. It has five tabs. Open `app/planner.html#day` (or `#why`, `#plan`, `#evidence`, `#pilot`) to start on a given tab.

1. **Why:** the driver breakdowns from `src/why_drivers.py` (see "Why the numbers move" below), read from the generated `app/why_data.js`.
2. **Day explorer:** pick any date from Jan 1 to Jun 30 and a branch (or all branches). The tab shows the day's orders against the frozen Jan-Mar model's expectation, with a Poisson z-score. It shows a traffic/basket/margin waterfall: a symmetric 3-factor Shapley split of gross profit against a reference built from expected orders and the Mar 4-31 basket and profit per item, which is accounting, not a cause. It also shows the day's time-of-day mix against the training mix for that weekday, observed weather at the three candidate locations, and events active that day with their verification status, branch exposure and source (from `data/external/external_events.json`, the holiday list and Ramadan). It ends with the ten most unusual days, alongside how many would be expected by chance (7 of 181 network days reach |z| ≥ 2, against about 8 expected). This is the interface task requested in EXTERNAL_CONTEXT.md. The UI retains its separate `src/day_ledger.py` → `app/day_data.js` export (and `reports/day_ledger.csv`). The more detailed source-linked `reports/daily_why_ledger.json` and `src/explain_day.py` are also committed; for June 24 the traffic part agrees closely (−$202 here vs −$200.22 in EXTERNAL_CONTEXT.md). The issued-forecast versus observed-weather comparison is available in the committed context cache and CLI dossier; it is not shown in this UI tab.
3. **Today's plan:** the decision card's forecast, opening quantity, a remaining-at-16:00 input that returns the top-up quantity, the full lookup table, cost assumptions, event-adjustment status and a permanent "historical replay" banner. Its only built-in cards are the two checked examples quoted in AGENTS.md. Load `reports/decision_cards.json` or a JSON printed by `src/predict_strict.py` / `src/recommend.py` with **Load cards**. If a remaining-stock value is not in the card, the page shows the CLI command to run instead of guessing.
4. **Evidence:** the held-out outside-factor results, read from the generated `app/evidence_data.js` (or load `reports/external_factor_test.json`). It also explains why outside events are review alerts, not forecast inputs.
5. **Pilot log:** one row per branch, product and day, covering arm (planner / current / shadow), recommended vs actually prepared, remaining at 16:00, top-up, sold, left at close, sell-out time, price, cost and override reason. Rows stay in the browser until exported as CSV (schema: `data/pilot/pilot_log_template.csv`). The page shows waste %, sell-out rate, overrides and contribution per item-day by arm.

`python src/pilot_report.py <exported.csv> [--json out.json]` produces the same summary. It adds planner-minus-current contribution per item-day with a 95% bootstrap interval over whole branch-days, and flags results with fewer than 20 branch-days per arm as not decision-grade. Unmet demand is not observed in a pilot, so service is reported as sell-out rate and time, never as a fill rate.
